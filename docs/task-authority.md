# Explicit background task authority

A direct authenticated user can assign authority when submitting `CreateTaskRequest`, by setting `authority_assignment` to `TaskAuthorityAssignment(expires_in_seconds=28800, max_access_level=20)`. Services and OBO callers cannot opt into this independent authority. The gateway checks the user's permission to create a task in its workspace before minting the grant. Applications must obtain explicit user consent for background execution; do not silently set this field on ordinary chat messages.

The grant is scoped to the task workspace and the user's current ACL permissions, permits only read (10) or read/write (20), and has a mandatory duration of at most 24 hours. Its expiry is also its renewal ceiling. The task, approving user, and requested duration are recorded. The grant is independent of the browser session: disconnecting, closing the tab, or ordinary session expiry does not revoke it. Cancel the task or revoke its root authority grant to stop access. Workspace ACL revocation still applies. Applications must enforce any narrower input/document scope recorded in their immutable task payload.

`required_downstream_authority_hops` accepts 0–8 and is the budget retained by the final worker. POOL assignment reserves one additional hop for the pool anchor. Every descendant inherits the reserved `authority_task_lifetime` constraint, even if the delegate or audience changes. Resolution fails closed when the original task is no longer pending/assigned/running or its live status is unavailable. Descendants cannot replace or remove this constraint. Legacy session-bound and agent startup grants retain their existing behavior.

For worker-to-service handoff, use `SendMessage.authorization` and `authority_continuation`. The gateway stamps `IncomingMessage.forwarded_authorization`, bound to the exact selected service. Service continuations can request `remaining_hops` (bounded by the parent minus one) and `expires_in_seconds` (default 300, maximum 900, capped by parent expiry). Agent continuations remain nondelegable and require checked-access attenuation. Custom-duration or delegable continuations are minted per invocation. Receivers must discard payload-authored forwarding fields and use only trusted transport metadata; never replace invalid task authority with service or browser-session authority.

Example pipeline budget: worker retains 3 hops; bridge continuation retains 2; a task delegated to an agent retains 1; the agent's tool-catalog continuation is a leaf. Each independently requested continuation remains bounded by the original task's expiry and lifetime. Cancelling a task prevents further authorized operations; it cannot retract data already read or an external request already in flight. Durable task authority does not itself provide process restart recovery or shared application request state.
